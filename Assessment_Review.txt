Explanation of the changes beyond code formatting:

- Q8: The question did not require Completed orders, unlike other questions that explicitly did. All order statuses, including Cancelled,
  were included as an analysis of recorded order contents. The old filter was an undocumented decision; the new semantics are explicit.
- Q15: The phrase changed over time includes 100 -> 120 -> 100. The product now appears with a final difference of zero rather than hiding its price changes.
  EffectiveFrom is unique per product, so joining the earliest record does not duplicate results.
- Q19: The phrase avg product rating was interpreted as averaging each product's ratings, then averaging those product means with equal weight.
  A product with 100 reviews does not receive more weight than a product with one review. Unreviewed products are excluded rather than assigned a zero rating.
  Q10 and Q20 average the vendor's individual review ratings; this distinction is intentional and documented at the top of the files.
- Q11 and Q13: Comparing with > after aggregation preserves competition ranking: 1,1,3. COUNT(DISTINCT Total) is not used because it would produce 1,1,2.
- Q10 and Q20: The unsold product count equals the vendor's catalog product count minus the count of its products appearing in completed orders,
  regardless of Quantity. Sales and reviews are aggregated separately to prevent revenue multiplication.

5 - Relationships, Keys, and 3NF ? Part 5
====================================================================================================

Diagram key: A [1] ---> [0..N] B means each B belongs to one A, and A may exist without any B rows.


Customers [PK CustomerID]
  +--[1 : 0..N]--> CustomerAddresses [PK AddressID; FK CustomerID]
  +--[1 : 0..N]--> Orders [PK OrderID; FK CustomerID]
  |                  +--[1 : 0..N]--> OrderItems [PK OrderItemID; FK OrderID, ProductID]
  |                  +--[1 : 0..N]--> Payments [PK PaymentID; FK OrderID]
  |                  +--[1 : 0..N]--> Shipments [PK ShipmentID; FK OrderID, VendorID]
  +--[1 : 0..N]--> Reviews [PK ReviewID; FK CustomerID, ProductID]

Vendors [PK VendorID]
  +--[1 : 0..1]--> VendorDetails [PK+FK VendorID]
  +--[1 : 0..N]--> Products [PK ProductID; FK VendorID]
  +--[1 : 0..N]--> Shipments [FK VendorID]

Products [PK ProductID]
  +--[1 : 0..N]--> OrderItems [FK ProductID]
  +--[1 : 0..N]--> Reviews [FK ProductID]
  +--[1 : 0..N]--> PriceHistory [PK PriceHistoryID; FK ProductID]
  +--[1 : 0..N]--> ProductCategories [PK (ProductID, CategoryID); FK ProductID, CategoryID]
                         <--[0..N : 1]-- Categories [PK CategoryID]


Each repeated table name in the diagram refers to the same table, not an additional table.
VendorDetails uses VendorID as both PK and FK: details cannot exist without a vendor, and each vendor can have at most one details record.
The details are optional, making 1:0..1 an appropriate implementation of the 1:1 relationship requirement.
ProductCategories implements M:N using a composite key, without arrays or lists of IDs stored in Products.
Orders -> Payments allows a failed attempt followed by success; Orders -> Shipments allows fulfillment across multiple vendors/shipments.

Normalization:
1NF: Each column holds one value. Addresses, order items, and reviews are not lists inside a customer/product row.
2NF: ProductCategories has a composite key with no attributes dependent on only part of that key. The other tables have clear row keys.
3NF: Customer, vendor, and category names are not copied into junction tables or order items. Each entity's attributes remain with that entity.
Revenue aggregates and order totals are not stored because they can be derived and would require synchronization after each change.
UnitPrice is a historical fact at purchase time, not a synonym for Products.Price; catalog price changes do not change old orders.
Products.Price is a stored copy of the current price in PriceHistory. This intentional redundancy speeds up catalog reads;
the risk is inconsistency if either value is updated directly. SetProductPrice is the supported write path and updates both atomically.
The procedure does not make every direct DML operation safe; the backend should grant its runtime account EXECUTE on the procedure
without granting direct updates to the price or price history. db_owner/sysadmin can inherently bypass this policy.

Data types and constraints:
- DECIMAL(10,2) is used for money instead of FLOAT to avoid approximate representation errors; aggregates benefit from SUM's wider precision.
- INT IDENTITY is used for keys at this scale, with BIGINT inputs for Quantity aggregation to avoid overflow at 2,147,483,647 units.
- NVARCHAR supports multilingual text, DATE is used for dates of birth, DATETIME2 and UTC for events, and BIT for binary states.
- UNIQUE protects emails; CHECK enforces nonnegative prices/stock, positive quantities, ratings of 1..5, valid statuses, and shipment/price dates.
- UNIQUE(OrderID,ProductID) allows one product row per order; UNIQUE(CustomerID,ProductID) prevents duplicate reviews.
- A price interval [from,to) includes its start and excludes its end. Adjacent records are allowed; a trigger rejects overlaps.
- A filtered index permits at most one default address without requiring one. It also permits at most one open price record.
  An open record for every product is ensured by the seed data and price-update path, not by a constraint requiring history for every INSERT Products.
- Financial history has no cascading deletes; deleting a referenced entity requires an explicit decision instead of silently losing old orders.

6 - Engineering Considerations Not Stated as Detailed Instructions
====================================================================================================

+----------------------------+---------------------------------------------------+---------------------------------------------------------+
| Concern                    | Decision / implementation                         | Why it matters                                          |
+----------------------------+---------------------------------------------------+---------------------------------------------------------+
| 1:N fan-out                | Aggregate sales/reviews/catalog independently     | Do not multiply money by reviews or payment retries     |
| Multi-vendor orders        | COUNT(DISTINCT OrderID) per vendor                | One order may count once for several vendors            |
| Category overlap           | Full revenue credit to each assigned category     | Category revenues cannot be summed as company revenue   |
| Rank ties                  | Competition rank; compare strictly greater totals | 1,1,3 rather than 1,1,2                                 |
| Second-highest price       | Second distinct level; return all ties            | Two equal-priced products alone have no second level    |
| Missing month              | Join to exactly previous calendar month           | Never compare to last available month across a gap      |
| Zero denominator           | Growth NULL when previous revenue is zero/missing | Avoid divide-by-zero and fake growth percentages        |
| Unknown rating             | Keep NULL; do not force zero                      | No review is not a bad review                           |
| Cancellation semantics     | Q2/Q8/Q17 any status; sales metrics Completed     | Never impose one status filter on all questions         |
| Price cycle                | Include original -> changed -> original           | Net zero change does not mean no historical change      |
| Concurrency                | UPDLOCK/HOLDLOCK + transaction on price path      | Serialize writers and avoid overlapping price intervals |
| Clock boundaries           | Single UTC seed clock; adjacent exact timestamps  | Avoid tiny history gaps and future completed fixtures   |
| Retry after failed seeding | Reject consumed identities                        | A rollback does not rewind identity values              |
| Query restrictions         | No CTE/window functions in Q1-Q20                 | DDL locking WITH(...) is a table hint, not a CTE        |
+----------------------------+---------------------------------------------------+---------------------------------------------------------+

Explicit decisions within the assessment's scope:
- Q6 also returns all of a vendor's products tied at zero sales. A vendor without products has no product to appear in Q6.
- Q9 shows months with completed orders. It does not generate a calendar or rows for every empty month; growth is NULL when the preceding month is absent.
- Q4 returns at most ten results, with CustomerID breaking ties; WITH TIES is not added because the requirement is Top 10.
- Q5 uses an exact 90-day cutoff; an order exactly at the boundary counts as activity within the period and is excluded from the inactivity result.
- Q17 counts year and month together; Q18 uses DATEADD(MONTH,1,...) to handle December -> January.
- Grouping only by customer/product name is incorrect when names repeat; keys remain part of the grouping.
- Revenue here is the sum of completed order lines, not the sum of payment attempts or accounting net revenue after refunds/tax.

System boundaries to consider when building a real backend, not hidden requirements claimed to be in the PDF:
Inventory reservation needs a quantity-guarded UPDATE inside a transaction; StockQuantity >= 0 alone does not make checkout safe.
Preventing duplicate payment requests requires an idempotency key and a clear provider policy; simply aggregating Payments does not solve it.
Shipping needs an order address snapshot from purchase time and shipment-item links if partial shipments must be tracked.
A Review is not conditional on a purchase because the question did not require verified purchases.
Price changes use the procedure; potential deadlocks across transactions are handled by retrying the entire transaction.
No checkout, payment gateway, or partial-shipment schema was added outside the scope of this SQL design/analysis assessment.

7 - Indexing and Scalability ? Design Decisions
====================================================================================================

1) Narrow numeric keys and unique junction keys reduce index width and prevent duplicate junction rows.
2) ProductCategories has two access paths: a PK starting with the product, and a (CategoryID,ProductID) index starting with the category.
3) Orders(CustomerID,OrderDate) INCLUDE(Status) supports customer history, while Orders(Status,OrderDate)
   INCLUDE(CustomerID) supports completed-order filtering and time-based reports. Column order reflects the query's starting point.
4) OrderItems(ProductID,OrderID) INCLUDE(Quantity,UnitPrice) serves product reports; an OrderID index covering
   amount, quantity, and product serves order reports. The existing unique constraint alone does not cover Quantity/UnitPrice.
5) Reviews(ProductID) INCLUDE(Rating) avoids a row lookup for the rating. Products(VendorID)
   INCLUDE(ProductName,Price) covers common vendor reads. Clustered keys are carried in nonclustered indexes.
6) Filtered indexes enforce invariants on small subsets of rows: default addresses and current prices.
7) Not every column gets an index. Each new index adds insert and storage costs; retaining it is based on measured access paths.
8) Separating order facts from historical prices preserves analytical results when the catalog changes. The tradeoff is more records and an explicit write policy.

A small test does not guarantee scalability: comparison-based customer/product ranking can reach O(C^2) or O(Pv^2)
even after aggregating facts once for each side. This follows from the restriction against window functions; no prohibited function is added to hide it.
If future requirements allow it, maintained summary tables or a reporting engine can be evaluated, but they are not required for the current solution.

Semantics / duplicate prevention: Aggregate completed-order units, then use an anti-comparison to exclude a product when a higher-selling product exists for the same vendor. ProductID prevents identical names from being merged.
Indexing: The product-oriented OrderItems index covers Quantity; Status/OrderDate helps read completed orders.
Scalability: Repeatedly comparing each product against its peers may become more expensive as the vendor's product count grows. Separating sales aggregation or using a summary table is a future option within business constraints.

10 - Running the Scripts and Repeating Measurements
====================================================================================================

Run on SQL Server with permission to create a database. Do not rename a database containing prior work to the test database name.
ECommerceDatabase.sql explicitly selects MultiVendorECommerceAssessment. Indexes and SeedData require the same database context.
This is an initial-creation design, not a migration for recreating existing tables. The project files contain no DROP DATABASE.

From the project root, using Windows Authentication:
sqlcmd -S "localhost\SQLEXPRESS01" -E -b -i "Data\ECommerceDatabase.sql"
sqlcmd -S "localhost\SQLEXPRESS01" -E -b -d MultiVendorECommerceAssessment -i "Data\Indexes.sql"
sqlcmd -S "localhost\SQLEXPRESS01" -E -b -d MultiVendorECommerceAssessment -i "Data\SeedData.sql"
sqlcmd -S "localhost\SQLEXPRESS01" -E -b -d MultiVendorECommerceAssessment -i "Data\Queries.sql"

The -b option matters: it stops sqlcmd on an error. GO is a batch separator understood by sqlcmd/SSMS, not a SQL command to send directly through a driver.
Queries/Qn.sql can be run individually. Data/Queries.sql combines queries only; it does not merge the schema and data scripts.
If an individual query is changed, update its copy in Data/Queries.sql as well; their equivalence was checked automatically in this review.

For an actual execution plan in SQL Server, use STATISTICS XML instead of the unsupported generic EXPLAIN syntax:
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
SET STATISTICS XML ON;
-- Paste the required query from Queries here.
SET STATISTICS XML OFF;
SET STATISTICS TIME OFF;
SET STATISTICS IO OFF;

To measure time alone, disable XML during timed batches and collect the plan in a separate batch, as done in this review.
Do not clear shared plan or data caches on a machine used by others for the sake of a benchmark.

Supported price-update path:
EXEC dbo.SetProductPrice @ProductID=1, @NewPrice=30.00;

When the procedure runs inside a caller's transaction, it does not COMMIT that transaction. It creates a savepoint; if a failure makes the transaction
uncommittable, the caller must roll it back completely. Updating within a transaction and concurrent updates from two connections were tested.
Backend account permissions and initialization of new products are the application layer's responsibility; do not grant the account db_owner.
